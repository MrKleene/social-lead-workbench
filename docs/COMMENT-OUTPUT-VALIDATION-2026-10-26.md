## 修复及边界

旧 `validateQwenEvidence` 使用 `redactText(reason) === reason` 判断理由是否合法。旧上下文脱敏规则会改写英文、数字、组合 Emoji、联系方式及部分中文短语，因此正常理由也存在被拒风险。本轮删除这一理由相等性检查，保留理由为非空字符串及 1–1000 字符上限；不归一化、截断或改写理由。

这只能证明代码存在过宽校验，**不能证明现有 INVALID_EVIDENCE 历史失败来自该分支**。旧记录没有保存具体校验分支、返回条目位置或被拒模型输出；本轮不猜测、不回填。

- 输出 JSON、根结构、字段类型/取值、数量、临时 ID 格式/重复/未知、理由结构、证据结构/来源/引用长度、评论证据缺失、非原文逐字引用和上下文脱敏占位符分别使用白名单子码。
- 示例：`OUTPUT_EVIDENCE_NOT_EXACT_ITEM_2` 表示模型返回的第 2 条引用不是对应外发原文中的逐字片段。这个编号是**模型返回位置**，不是整帖评论的全局编号；数量或根结构错误无法定位条目时不伪造编号。ID 对齐仍支持返回顺序变化。
- 严格保留 exact source substring 校验、必须有 COMMENT 证据、输入策略及上下文脱敏约束、字节和响应大小限制、提示注入防护、身份授权、预算/间隔、幂等和取消守卫。
- 新错误使用既有 `SemanticModelCall.errorCode` 与 review/job reason 字段保存；无需新 schema 或迁移。返回 `outputFailure` 包含安全子码、序号和固定说明，幂等命中也可读取同一诊断，不重新调用。
- JSON/schema 异常不直接暴露 Zod issues、模型原文、引用、联系方式、临时 ID 值或 Key。日志与 Git 中只有代码、固定说明和明确的合成测试数据；既有评估输入留存范围没有扩展。
- 一个输出校验失败仍使本批整体不采纳，不产生部分评分、不自动重试。所有受影响行的原因明确说明“本批整体未采纳，不代表每条评论均独立校验失败”。手动任务显示“批次未采纳”与“未送审”，区别已尝试批次和剩余未处理评论。
- API 的只读 `displayReason` 和前端对旧 `INVALID_EVIDENCE` 显示“旧记录未保存具体原因”，保留原始 reason、历史输入、结果、版本和状态，不进行历史数据库写入。
- 原文评论、目标/模型锁定、上下文范围及原有系统提示防护未改。模型理由只按文本渲染，不执行 HTML、脚本或指令。
