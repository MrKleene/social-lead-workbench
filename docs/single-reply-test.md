# Bounded one-comment operator test

The operator entry `node scripts/run-single-reply-test.mjs --execute-approved-once /absolute/private-scope.json` consumes an explicit, expiring scope containing one account, stable sender/recipient/post/comment IDs, review version, independent template, exact text, approved binary hash, maximum one submission and no retries. The file must be an owner-only regular file. It is not a queue or HTTP endpoint.

It records the authorization and reserves the existing REAL recipient ledger, configured Asia/Shanghai account-day quota and platform lock atomically. Reusing the same approval returns its receipt; a prior recipient attempt blocks another approval across accounts/channels. Live saved-session identity and new-protocol capabilities must match before the scope is checked again and one send call is permitted. The narrowly recognized read-only account pause is retained throughout; platform risk pauses are never overridden. All automatic contact rules must stay OFF; the global deployment enable record remains OFF.

New scopes use the explicitly reviewed build table in `single-reply-builds.ts`: SHA256 `dd91f1991cfa2041b9e6e63573813c9144e0017f1ef074e6b79f3aa44193237b`. This is a compatibility allowlist, not installation or execution permission. The old `ee0901ef...` is historical only and is rejected for new scopes. It has no reliable response mapping, so this path never records CONFIRMED. Proven pre-submission refusal releases quota once but consumes the authorization. Ambiguous outcomes retain recipient protection and quota; uncertain process shutdown or risk pauses the platform. Never rerun after a timeout: inspect the durable attempt and audit first. Installation alone does not authorize any account, content or target.

Offline validation: 730 API tests, PostgreSQL migration/preservation and integration tests, runtime pin tests, workspace types and build. Synthetic tests do not establish real delivery. Actual scopes and live evidence are private operational artifacts, not repository fixtures.

Diagnostic results now preserve only whitelisted stage/error and identity-consistency enums in the normalized pre-submit reason and final audit. Arbitrary properties/IDs/errors are rejected. Historical records are not rewritten. The diagnostic candidate does not change the one-shot approval hash or grant reauthorization of any prior recipient. A future explicitly authorized reattempt must preserve and reference its prior proven NOT_ATTEMPTED record; the current entry deliberately rejects any prior non-cancelled recipient attempt.

## Versioned authorization and installed v2 diagnostic binary (2026-10-27)

A new private scope must explicitly include `scopeVersion: workbench.single-reply-authorization.v2`, `purpose: SUBMIT_EXACT_COMMENT_ONCE`, `protocol: workbench.xhs.exact-reply.v1`, and one hash from the source-reviewed allowlist. There are no defaults or conversion from preflight/legacy scopes. Account, sender, exact recipient/post/comment/text, review and availability versions, fresh approval UUID, expiry, one submission and zero retries are still required. The owned runtime and transport use that same scoped hash; the actual executable is rehashed by `inspectTools` before spawning. Unknown hashes, wrong protocol/purpose or a different installed pin are rejected before acquisition. No automatic sender deployment flag or account setting is changed.

The installed `dd91f199...` source retains exact-reply v1 and separate preflight v2. `CRM_EXACT_PREFLIGHT_ONLY=1` registers only preflight and omits legacy HTTP routes; it wins even if a send variable is present. Normal process environments remove inherited enable variables. Exact send remains OFF unless an independently authorized one-shot runner explicitly opens its owned reply process. The reply transport still requires the new capability handshake; read-only/legacy servers cannot send through it. This change does not alter the binary, tools, selectors, cancellation, confirmation rules or default deployment state.

### Durable diagnostic evidence

The stage-journal executor requires the explicitly negotiated `workbench.reply-stage-journal.v1` capability. `RPC_INTENT` is committed before dispatch; it links the existing request key to the protocol UUID used in the private journal filename. `RPC_RETURNED`, a fixed `RPC_ERROR` category, and `TRANSPORT_STOP` are separate append-only audit events. The before-submit/attempt-intent/after-click/driver-close journal is fsynced locally and read only after confirmed owned-stop. A missing, torn or invalid journal, an audit failure or absent durable capability cannot justify retry, success or a quota refund. ATTEMPTED intent remains 0-or-1 after a crash; AFTER_SUBMIT means only that the click call returned. The prior UNKNOWN test history is never retroactively interpreted or rewritten.
