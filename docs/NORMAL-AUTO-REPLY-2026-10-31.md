## 结果与原因

普通入口的代码闭环已经接通：保存并开启规则 → 正常采集 → 每帖全部待评评论一次模型匹配 → 高分且证据充分的评论入队 → 发送前账号检查 → 精确目标提交 → 独立回执核验 → `/reply-history`。没有添加逐条人工审核，也没有让采集依赖模型。

此前有两个实际断点：正常发送器没有刷新当前运行周期的账号检查，导致资格过期后无法领取任务；普通 MCP 构建的响应映射仍为空，成功响应也不能成为确认回执。本轮复用已验证的账号检查及历史捕获响应字段，补齐两者，未仅去掉能力开关。

发布状态仍是**已实现、隔离验证通过，未安装到正式运行实例、未做普通入口真实实发**。`xhs-reply-deployment.ts` 固定离线候选哈希与审阅状态，`enabled:false`；`runtime/platform.cjs` 仍固定旧已安装哈希。本轮没有安装候选、重启正式后台、开启生产规则或触发存量队列。因此用户当前 63968 仍可能显示“未开放”，不能把代码提交表述为已经上线。

## 实现与保留边界

- `AutoContactService` 先在事务内执行去重、恢复及领取；确有已授权的 `WAITING_ACCOUNT` 任务时，事务外调用只读资格检查，再重新领取。检查失败不占额度；同账号并发共享一次检查，暂时失败至少退避 60 秒。规则版本、授权人、模型、目标及平台状态在发送前重新校验。
- 账号检查绑定当前保存会话、设备、运行周期和稳定账号 ID；响应到达时重新检查账号版本及引用。身份不符、登录失效、限制提示、历史限制和停止未确认均不能授权提交。已登录不等于有发送资格；没有平台提示也不保证平台接受发送。
- 保存/启用配置允许“已有保存会话、等待发送前检查”的账号；后端提交资格仍独立检查。已知受限账号仍不可用。没有新增手动暂停状态，账号用途继续由采集／回复配置选择决定。
- 实际发送进程再次检查登录身份。RATE_LIMITED/RESTRICTED 保留风险语义，停止相关规则；停止未确认保留设备租约。历史 UNKNOWN 的接收者锁、额度和记录不改动，不换号或跨渠道重发。
- 固定响应映射校验 endpoint、HTTP 状态、success、code=0、帖／目标评论／接收者／发送者／原样内容及新评论 ID；还必须独立重新加载查到相同元组，并确认所属进程停止，才记录 CONFIRMED。缺失或矛盾证据保持 UNKNOWN。不会重复提交来“补验”。
- 平台共享日额度、跨账号与渠道用户去重、勿联系、规则版本和模型结果绑定均沿用原有事务逻辑；没有 schema 迁移或账本重建。
- `/home` 配置、`/automation` 本轮步骤/结果、`/work` 全项目概览、`/reply-history` 独立记录保持分工。设置继续用弹窗和内容区中央 loading；错误保留草稿、可恢复。
- REQ-013 中针对“对方后续消息”的自动回复仍依赖未接通的收件箱同步；本轮完成的是 REQ-011 的高匹配评论首次触达，不把两者混为一谈。私信、抖音和 Windows 原生发送不在本轮验收范围。
