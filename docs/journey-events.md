# Task progress transport

Progress uses the existing authenticated `/api/events` SSE endpoint. The database remains the source of truth. The API listens on PostgreSQL channel `crm_journey_v1`; display-only triggers publish invalidation identifiers after transactions commit. Workers never publish before saving their state. The payload carries no post/comment text, account identity, credential, or execution authority.

Clients subscribe before requesting a snapshot. Initial `ready`, reconnect, and listener recovery invalidate the permission-checked task queries. A 120 ms debounce combines rapid changes; run/config scoping keeps historical task views independent. Repeated event IDs are discarded. Out-of-order change events only cause a fresh read, never overwrite results. Heartbeats can extend only an identical execution ID/session/phase already present in a snapshot; new phases cause a snapshot read. They cannot resurrect terminal results.

Healthy journey queries do not use the old 2-second polling. The SSE connection has a 15-second heartbeat and 60-second snapshot repair signal for missed events. Broken/missing streams use a 30-second read fallback. Browser offline/online events and a 45-second transport watchdog recover stalled streams. Execution evidence still expires after 15 seconds: unavailable evidence must not show an endless sending spinner. UNKNOWN remains visible through connection failures. Other independent product queries retain their existing refresh rules.

Only ADMIN receives task identifiers. Each emitted message checks live session/user/refresh-grant authorization. Logout/unmount/shutdown closes listeners and timers. The database listener verifies migration installation, probes the connection every 15 seconds, and reconnects with 1–30 second backoff. Trigger errors are nonfatal to business writes; queue pressure drops display notifications and the periodic snapshot repairs the display. A missing trigger migration degrades to fallback reads.

This stream is not a durable event log or an execution queue. Reload recovers current truth, and existing persisted journey audit records provide recent phase history. It does not replay every transient animation or synthesize progress for legacy tasks. Multiple tabs use separate authenticated SSE connections (browser HTTP/1 connection limits still apply). No changes to worker scheduling, authorization, quota, deduplication, UNKNOWN handling, or business state transitions.

Validation: `packages/domain/test/events.test.ts`, `journey-push-postgres.test.ts` (isolated `crm_test` only), `apps/web/src/lib/journey-event-sync.test.ts`, and journey step-state tests. A localhost mock browser harness covers real EventSource transport, 1440/320 layouts, reconnect, missed phases, history selection and two tabs without platform/model/sending calls.

Deployment requires migration `202611030002_journey_push` and one API-process reload in an idle window. The migration adds a function and eleven triggers; no business rows, columns, or history are rewritten. Rollback application code only in an idle window; the notifications are harmless to the old client. If removing transport infrastructure later, drop only `journey_push_*` triggers and `public.crm_journey_notify()` in a forward migration, never restore or delete business data.
