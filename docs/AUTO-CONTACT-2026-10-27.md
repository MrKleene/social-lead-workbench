## 已实现

- 评论审核页和账号中心可进入 `/auto-contact`。管理员独立设置阈值、审核目标、评论/私信渠道、原样发送文字和账号池；初始内容空白、自动联系关闭。保存后仍关闭。开启需要确认这版规则的范围；生产适配器不可用时 API 和 UI 均拒绝开启。
- worker 在审核调度后扫描新审核结果，接收足够分数、`MATCH`、`SUFFICIENT` 和真实逐字评论证据；不需要每条人工批准，但已拒绝、勿联系及真实人工联系历史仍阻断。不创建销售线索。授权范围明确为开启后更新的审核结果，不偷偷批量处理全部历史结果。
- 队列锁定目标、模型、规则和审核证据版本；配置保存、关闭、版本变化会取消尚未尝试任务。最终调用前再检查权限、账号、日期、额度、来源和证据。分页面展示不会限制候选总数：扫描每次最多 100 条未处理结果，后续 tick 继续剩余条目，已验证 106 条全部进入队列。
- 回复绑定已审核评论自己的 `postId + commentId + userId`，核对归档关系；不借用该旧评论的 `targetComment`。私信使用同一个稳定作者 ID，缺失、冲突或非支持 ID 失败关闭。
- 复用 `PlatformIdentity`、`ContactLedger`、`ContactAttempt` 和 `AccountDay`。平台 + 稳定用户 ID 唯一身份，模式内账本唯一，事务 advisory lock、账号行锁和唯一请求键共同防重复。不同账号、不同渠道、不同规则也不能重复首次联系同一用户；排队取消可以重新分配，已尝试/成功/未知/明确失败不会自动重试或换号。
- 每账号评论与私信共用日额度；新自动联系使用 `REAL:Asia/Shanghai:YYYY-MM-DD`（隔离模拟为独立 `SIMULATION`），上海零点换日，旧 UTC 桶保留。成功、预占/在途、未知和剩余分开显示。当前账号满额时只给其他健康授权账号分配其他用户，全池满额等待。规则存下已确认上限，账号中心单独提高额度不会扩大旧授权；降低额度立即约束。账号版本冲突拒绝覆盖用户并发修改。
- 一个平台同一模式同时最多一个在途发送。平台限流、验证、封禁、拒绝均锁住整个相关发送工作流并关闭相关规则，不切号绕过。未知保留收件人与原日额度；60 秒超时、连接异常、失效回执或进程中断按未知处理。核查确认未发送才释放原日额度，重复核查不重复释放。
- 台账保存规则/审核版本、收件人、来源、发送账号、渠道、实际尝试内容、尝试时间、确认回执及结果；排队、预占、尝试、确认、失败、未知分别呈现。模拟记录有独立模式和标签，不能显示“已送达”。UI 以纯文本显示内容和证据，不执行模型/配置字符串。

## 真实发送为何仍不可用

工作台当前集成的 `apps/api/src/collection/mcp/policy.ts` 只允许 `check_login_status`、`search_feeds`、`get_feed_detail`；`transport.ts` 对白名单外工具拒绝。现有平台能力表也没有可用发送闭环。本轮没有更换已批准 MCP 二进制、扩宽白名单、安装软件或获取新凭据。

新增 `ContactSender` 只定义能力、账号健康、准确目标、发送结果和可选回执查询契约。生产 DI 固定注册 `UnavailableContactSender`，无环境变量或 HTTP 参数切换到模拟发送的后门。只有隔离测试通过 Nest provider override 注入合成 sender。这里证明的是本项目尚未接通受支持适配器，**不是声称平台永远不支持发送**。

后续真实接通至少需要：确认受支持且能绑定指定账号/稳定收件人/准确评论目标的发送方式、可核验回执及限流分类；专门审查会话/设备授权和中断处理；用户提供实际内容及账号/阈值/渠道规则；另行批准有界真实发送验收。不能仅取消 `UNAVAILABLE`。目前没有平台暂停解除或收件人重新解锁入口，未知只能在适配器提供只读回执核验后解决，不能伪造成功或直接清锁。
