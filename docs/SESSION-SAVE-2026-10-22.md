# 扫码会话保存确认与同账号更新（2026-10-22）

基线 `8467f65`；REQ-006/022/024/026/027。此轮完成代码与隔离测试，**正式 API/worker 未重启，新后端能力尚未加载**。没有真实扫码、读取已有 Cookie、替换真实会话、采集、模型或发送。没有 schema、启动器、设备身份、vault 或系统权限变更。

## 用户流程

入口 `/work?module=accounts`。首次添加账号，在抽屉明确同意本机保存后生成二维码；依次呈现等待扫码、平台确认后保存中、已保存到本机。保存失败不能显示已保存。后台升级前，前端保留原能力和原文案，不假报保存成功。

已有账号在原批准设备上可选择「重新扫码」，一次明确确认“仅同一账号核验成功后替换”。必须扫描同一个小红书账号。失败、取消、过期或身份不符均保留旧会话引用；不会更改负责人、任务归属或解禁平台受限账号。设备归属不符、遗留引用不完整时仍拒绝自动替换。

已保存只表示本机文件和引用已确认，不代表登录永不失效。正常重启保留文件，并把在线状态恢复为待主动核验，不在启动时自动请求平台。采集仍需独立单次授权，评论私信发送关闭。

## 上游证据与实现

官方源码的 [二维码后台等待逻辑](https://github.com/xpzouying/xiaohongshu-mcp/blob/a5c8f7799980ba1fdd501999843eb2d17e4c9a9f/service.go) 和 [Cookie 文件格式](https://github.com/xpzouying/xiaohongshu-mcp/blob/a5c8f7799980ba1fdd501999843eb2d17e4c9a9f/cookies/cookies.go)表明：二维码等待与保存异步，登录状态接口没有独立落盘成功字段，种子初始化可能先创建空 cookie 数组。文件存在、可解析或前端勾选均不足以证明会话已保存。这是公开源码依据；本轮没有实际调用当前平台二进制验证格式。

- 每次扫码只在既有执行电脑私有目录新建候选目录，不打开旧会话做写入。沿用现有目录，通常为系统应用数据目录下的 `SocialLeadWorkbench/devices/<device>/credential-roots/<root>/<account>/<attempt>/`；已批准的旧目录保持原位置。
- 平台状态必须明确已登录且返回稳定账号 ID。更新时必须与原平台、账号身份一致，昵称不参与身份认定。
- 新增持久 `SAVING` 阶段，二维码移除，保存窗口有界；没有新增自动平台重试。
- 停止本次会话写入进程后，独立检查候选元数据、私有文件归属/权限、非链接/单链接、1 MiB 上限、完整 JSON 和非空 cookie 结构。支持文档中的 v1 数组和 v2 envelope；空种子文件、无值、异常域名或重复 cookie 拒绝。离线夹具有独立结构，不冒充真实 Cookie。
- 通过受控文件句柄校验 inode/dev/大小/修改时间，执行文件 fsync；POSIX 同步候选与账号目录条目。失败统一返回安全原因码，不携带内容、文件路径或原异常。结构检查不等于平台永久有效证明，身份仍依赖平台状态。
- 原账号/新会话引用及登录结果在一个数据库事务内切换；重新检查账号版本、旧引用、平台身份、归档/限制状态、设备及有效执行租约。其他任务/恢复核验不能与真实会话更新共用执行租约。
- 不是原地覆盖旧 Cookie 文件：候选完整后原子切换数据库指针。事务失败旧指针保留，提交后意外断线不会撤销已提交结果。进程重启会取消未完成尝试，不擅自接纳未提交候选。
- 未引用的候选文件和旧版本保留在私有目录，不自动删除、复用或扫描接纳；当前没有自动垃圾回收。这样避免清理竞态删除仍被引用的文件，但多次失败会占用少量额外磁盘，后续清理需独立的引用核对流程。
- API 仅返回 `localSaved` 布尔证据和受控状态。证据使用既有 AccountLogin.reason 的 `LOCAL_SESSION_SAVED_V1`，无 schema 迁移。后台能力字段控制重新扫码入口；旧成功记录不追溯伪造落盘证据。
